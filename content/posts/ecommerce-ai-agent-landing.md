## 先看一个公式

电商所有业务动作都能归到一个公式上：

> **GMV = 流量(UV) × 转化率 × 客单价**

拉流量、提转化、提客单价，三个抓手。AI 在电商的每一个落地场景，最终都要回答一个问题：你动了这三个因子里的哪一个，或者你省了多少人力成本。回答不了这个问题的 AI 项目，立项都过不了。

这篇文章把 AI Agent 在电商的落地场景按成熟度排一遍序，重点讲清楚为什么售后客服总是第一站，最后给出一份从企业客服 Agent 迁移到电商场景的实操清单——这部分来自我自己做企业级客服 Agent 的经验。

## 五大场景，按成熟度排序

**1. 售后客服 Agent（最成熟）**

退换货、物流查询、退款进度。几乎所有电商公司的 AI 落地都从这里开始，下一节展开讲原因。

**2. 售前导购 Agent**

商品推荐、参数对比、尺码建议。难点是幻觉——推错货直接损失 GMV，甚至引发客诉。所以售前 Agent 必须强约束在商品库的实时数据上，模型只负责组织语言，商品信息一律走结构化查询，不允许模型"记忆"里的商品知识出场。

**3. 多语言客服（跨境刚需）**

Shein、Temu 要用几十种语言服务全球买家，传统方案是按语种雇客服团队，LLM 在这个场景是降维打击。广深的跨境电商公司在这个方向投入很重。

**4. 商家侧 AI 工具**

商品文案生成、主图生成、评论情感分析、经营诊断。B 端商家付费意愿强，是能直接收钱的场景。

**5. 数字人直播**

低成本 7×24 直播间。技术上能跑，但平台监管在持续收紧，合规风险高，把它排在最后。

## 为什么售后客服先落地

三个原因，每一个都站得住：

**流程和话术高度标准化。** 退换货政策是明文规则，物流状态是结构化数据。这类问题特别适合 RAG + 工具调用的架构，不需要模型发挥创造性——创造性在客服场景里是风险，正确率才是刚需。

**量大且重复度高。** "我的退款什么时候到账""物流到哪了"这类问题占客服请求的绝对大头。女装退货率能到 30%~50%，跨境更高，售后请求量就是这么来的。自动化的 ROI 一眼可见，省的是真金白银的人力成本。

**容错可控。** 答不好可以随时转人工兜底，损失有限。对比售前导购：推错商品直接损失成交，风险高得多。所以行业的落地顺序基本都是"先售后、再售前、再经营侧"，风险从低到高逐步放开。

## 电商客服 Agent 的标准架构

这套架构面试能画，实际系统也确实长这样：

```
用户消息
  → 意图识别（查物流？退货？投诉？闲聊？）
  → RAG 检索（售后政策、商品知识库）
  → Function Call 调工具（查订单接口 / 查物流接口 / 创建退款工单）
  → 敏感操作走人工审批（如大额退款）
  → 回复生成 + 全程质检评测
兜底：置信度低 / 用户情绪激动 → 转人工客服
```

几个工程要点：

- **意图识别用"规则先行 + LLM 兜底"**：高频意图（查物流、查退款）用规则 O(1) 直接命中，省 token 也省延迟；长尾和模糊表述交给 LLM。
- **敏感操作分级**：退款直接动钱，按金额分级——小额自动过，大额走人工审批。这不是提示词里写一句"请确认"，而是在编排层面做硬中断，审批通过前动作真实不会执行。
- **转人工是功能，不是失败**：置信度低、用户发火、多轮未解决，都要有明确的转人工触发条件，并把上下文完整交接过去。

## 从企业客服 Agent 到电商售后：迁移清单

我做过企业内部管理系统的智能客服 Agent（意图识别 + RAG + 业务数据联动 + 工单流转，已接入售后和技术支持团队日常使用）。把这套东西迁到电商售后场景，哪些能复用、哪些要改造，我的判断是这样的：

**架构层能直接复用：**

- 整体链路：意图识别 → RAG 检索 → Function Call → 人工兜底，这套骨架完全通用
- 多轮对话管理和上下文维护
- 知识库的构建、切分、检索流程
- 工单流转机制（Agent 解决不了转人工）
- 评测体系（badcase 收集、回归测试）

**业务层要动手改造：**

1. **知识库内容**：从产品文档换成商品信息、售后政策、物流规则。商品数据量大、变化快，知识库的增量更新机制必须先解决。
2. **工具层**：Function Call 的对接目标变成订单服务、物流查询、退款接口这些电商后端微服务。这要求你懂接口背后的业务语义——订单状态机走到哪一步了、这个状态下允许什么操作。
3. **并发和稳定性**：大促期间客服请求可能涨 10 倍，限流、降级预案要提前做。平时能跑和大促能扛是两回事。
4. **敏感操作管控**：退款按金额分级审批，前面说过。
5. **多语言**（跨境场景）：意图识别和回复生成都要支持多语言。

所以这件事对我来说是场景迁移：架构能力是现成的，要补的是电商的业务规则和数据对接。这也是我最近系统学习电商业务的原因——Agent 的工具调用对接的就是订单、工单这些后端接口，不清楚接口背后的业务语义和边界条件，设计不出可靠的 Agent。

## 收个尾

判断一个电商 AI 场景值不值得做，我的检查清单就三条：

1. 它动了 GMV 公式里的哪个因子，或者省了多少人力？
2. 答错的代价是什么，有没有兜底路径？
3. 数据是结构化的吗，还是要靠模型"想象"？

售后客服在三条上全是最优解，所以它总是第一站。
