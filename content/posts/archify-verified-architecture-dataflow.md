# Archify：把代码库转成能逐条核对的架构与数据流图

让 Agent 解释一个代码库，常见的结果是几段模块介绍和一张看起来合理的架构图。真正用于系统交接时，问题会变得具体：图上的鉴权发生在哪里？服务是否真的调用数据库？错误由哪一层转换？某个外部依赖究竟参与了请求，还是只在构建时使用？

[Archify](https://github.com/tt-a1i/archify) 值得研究的部分，是把图的生成拆成两个职责：Agent 提取并组织事实，程序校验结构并渲染产物。通过这条链路，可以学习怎样让架构文档具备可复核的依据。

> 本文归档于 2026 年 9 月，资料核对于 2026-10-14。工具命令参考已有的 2026-09-09 本地记录与提交 `10722002bb8777ecb639d93c49586fae4adf3ae4`；订单项目部分是练习设计，尚未生成实际架构图。

## 继续使用同一个订单后端

上一阶段用 [Ponytail](/blog/ponytail-agent-scope-control) 控制订单接口的实现范围。这一阶段沿用同一份代码：一条 `GET /api/orders/{id}`，一张 `orders` 表，以及从有效 JWT 得到当前用户的鉴权逻辑。

业务契约保持一致：用户只能查询自己的订单；未登录返回 401；不存在或归属不匹配返回 404；参数错误与数据库故障进入约定的错误响应。

先画清这一条请求，暂不加入代码里没有的 Redis、消息队列、支付系统和独立身份服务。如果令牌在本地验签，就表达本地校验器；只有源码实际访问远程密钥或身份服务时，才增加对应外部连线。

## 核心链路：事实提取与确定性交付

Archify 使用带类型的 JSON 作为中间表示，后续通过校验与渲染生成独立 HTML，图形部分使用 SVG。它提供架构、流程、时序、数据流和生命周期等图类型；应按要回答的问题选择。[固定版本 Skill](https://github.com/tt-a1i/archify/blob/10722002bb8777ecb639d93c49586fae4adf3ae4/archify/SKILL.md)

```text
代码库 / 已知系统描述
          ↓
Agent 提取模块、调用与边界
          ↓
结构化 JSON IR
          ↓
Schema、关系与布局校验
          ↓
HTML / SVG 产物
          ↓
对照源码复核，必要时补充运行证据
```

这里的 IR 可以理解为“机器能检查的图源文件”。它把节点、关系和类型从自然语言说明中分离出来，让生成结果能够保存、比较和重新渲染。

一个常见的误区是把 JSON 格式正确当成架构正确。程序能发现不合法字段、错误引用和部分布局问题，却无法仅凭一份图源证明业务服务真的经过了授权校验。语义事实仍然需要源码和运行证据支持。

## 架构图与请求流程分开回答

架构图回答“有哪些组件，它们如何连接”；请求流程或时序图回答“这次输入按什么顺序经过它们”。鉴权是一段逻辑时，不应为了凑一个节点把它画成独立部署的服务。

对订单接口，可以先列出需要核实的请求路径：

```text
HTTP 请求
   ↓
JWT 身份校验 ──无效或过期──→ 401
   ↓
路由参数校验 ──格式错误────→ 400
   ↓
订单业务服务
   ↓
带订单 ID 与当前用户 ID 的查询
   ↓
orders 表 ────没有匹配行───→ 404
   ↓
响应转换 ────访问异常─────→ 约定的服务端错误
   ↓
200 订单响应
```

这张文字图是练习目标，不代表某个已存在仓库的真实执行顺序。具体项目可能先做路由解析，也可能由框架异常处理器统一响应；生成正式图时，要按源码修正顺序和责任位置。

## 给每条关系建立源码依据

建议在图之外维护一张简短的证据表。下面的文件名是练习项目可采用的命名，实际路径与行号需要填入本次提交的真实位置。

| 图中关系 | 应核对的源码 | 要回答的问题 |
| --- | --- | --- |
| 请求进入鉴权 | 安全配置、过滤器或拦截器 | 这条路由是否真的被保护？ |
| 身份进入业务服务 | Controller 的参数与调用 | 用户 ID 是否来自可信身份？ |
| 服务调用数据访问层 | Service 的查询调用 | 订单 ID 和用户 ID 是否都传入？ |
| 查询访问订单表 | Repository 或查询语句 | `owner_id` 条件是否实际执行？ |
| 空结果返回 404 | 空值分支与异常映射 | 找不到时会不会变成 500？ |
| 查询故障进入错误响应 | 异常处理器 | 是否泄露 SQL 或连接信息？ |
| 系统访问外部服务 | 网络客户端和运行配置 | 是真实调用，还是仅有未启用配置？ |

节点证据和连线证据需要分开。某个类存在，只能证明有这个类；证明 A 调用 B，还需要找到具体调用。类名中出现 `Auth`，也不足以证明当前接口实际使用了它。

若源码依赖部署配置才能判断，应记录尚未确认的条件。例如密钥获取方式、代理转发和生产数据库地址，不能用一个漂亮的云服务图标代替验证。

## 再执行机器校验

在已有的固定版本实践中，先检查环境，再对 JSON 进行验证和交付。以下命令属于使用方式示意，路径需要替换为自己的候选图源；执行目录是包含 `bin/archify.mjs` 的 Skill 包目录。

```bash
node bin/archify.mjs doctor
node bin/archify.mjs validate workflow order-query.workflow.json --quality showcase --json
node bin/archify.mjs deliver workflow order-query.workflow.json order-query.html --quality showcase --json
```

图源字段应从匹配的 Schema 和示例读取，避免自行发明。遇到失败时，按诊断定位具体对象，修改相关节点或关系后重新校验。[作者契约](https://github.com/tt-a1i/archify/blob/10722002bb8777ecb639d93c49586fae4adf3ae4/archify/references/authoring-contract.md)

2026-09-09 的本地记录显示：随仓库提供的一个 Workflow 示例通过了 9/9 检查，交付结果为 0 errors、0 warnings。这份记录只证明当时那个示例的工具链可运行，订单图仍需单独验证。

交付成功后也要保留边界：确定性产物检查、浏览器行为检查和视觉阅读检查，支持的结论各有不同。固定版本文档明确区分了这些验证层次。[交付契约](https://github.com/tt-a1i/archify/blob/10722002bb8777ecb639d93c49586fae4adf3ae4/archify/references/delivery-contract.md)

## 一处鉴权变更，怎样体现在图里

假设查询原来只使用订单 ID，后来修正为订单 ID 与当前用户 ID 的联合条件。架构里的组件数量可能完全不变，但安全语义已经变化。

这时应更新查询关系的说明、补充归属不匹配的错误路径，并关联修复测试。若只重新生成一张相同的组件图，评审者仍然看不到这次变更解决了什么问题。

JSON IR 的价值就在这里：可以比较有意义的节点与关系变化，把图源、源码提交和验证结果绑在同一次变更上。图用于解释，证据用于确认，两者一起才适合系统交接。

## 验收一张图的四个问题

检查时可以按这个顺序推进：

1. 所有节点与边界是否能对应真实代码、配置或明确的外部依赖？
2. 所有连线是否有调用、查询或协议依据？
3. 正常路径、鉴权失败和错误路径是否覆盖本次业务契约？
4. 图源与产物是否通过工具校验，阅读时是否存在歧义？

完成这一轮后，下一步进入 [OpenCodeReview 与安全审计的证据核对](/blog/agent-code-review-security-evidence)。已经核实的请求链路，可以帮助评审 Agent 理解订单归属规则，也方便人工判断一条安全报告究竟缺了哪段证据。
