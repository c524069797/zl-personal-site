## RAG 的 Demo 和系统隔着一条鸿沟

照着教程搭一个 RAG：文档切块、embedding 入库、相似度检索、塞进 prompt——一个下午就能跑通。但"能跑"和"可信"之间隔着一条鸿沟：检索不准、答非所问、无法溯源、改了 prompt 不知道有没有变好。

这篇写我在企业客服 Agent 项目里把 RAG 从 Demo 推到生产可用的过程，每个环节都是真实迭代出来的。

## Chunk 策略：一刀切是万恶之源

最常见的做法是固定长度切块（比如 512 token 一刀）。这个做法在真实知识库上很快露馅：一条工单的"问题描述"和"解决方案"被切到两个 chunk 里，检索命中了问题却丢了答案。

我的做法是**按内容形态设计多粒度 Chunk 策略**：

- **工单摘要**：一条工单浓缩成一个 chunk（问题 + 结论），适合"这个报错怎么解决"类查询
- **工单讨论**：处理过程的关键讨论单独成 chunk，适合需要过程细节的场景
- **Wiki 整页**：短文档整页一个 chunk，保留完整上下文
- **Wiki 按标题拆分**：长文档按 H2/H3 标题切，天然的语义边界

配套的是 **metadata 富化**：每个 chunk 带上项目、模块、工单状态、责任人、更新时间。这些字段支撑三件事：检索时做元数据过滤（只查某产品线的文档）、回答时做来源溯源（引用到具体工单号）、维护时做增量更新（按更新时间刷新失效知识）。

用这套策略，知识库从最初 8 条 seed 数据扩展到 30+ 结构化 chunks 再到批量入库历史工单和 Wiki，检索质量没有随规模劣化——分粒度和 metadata 是关键。

## 检索：单一向量检索不够用

**向量检索的盲区是精确匹配。** 用户问"ERR_LICENSE_EXPIRED 报错"，向量检索可能召回一堆语义相近但错误码不同的文档——embedding 对错误码、型号、版本号这类 token 不敏感。

所以生产系统标配**混合检索（Hybrid Retrieval）**：BM25 关键词检索管精确匹配，向量检索管语义泛化，两路召回后融合排序，再加一层 Reranker 精排。我实测的经验：BM25 + 向量 + BGE Reranker 的组合，比纯向量检索的 top-3 命中率提升明显，尤其在错误码、专有名词查询上。

**GraphRAG 是补充，不是替代。** 它把知识组织成实体关系图，适合回答"跨文档关联"类问题（这个模块的负责人处理过哪些相关工单）。但构建和维护成本高，我的取舍是：主链路用混合检索，GraphRAG 只覆盖高价值的关联查询场景。别一上来就全量上 GraphRAG，大多数问题混合检索就够了。

向量库选型同理：Qdrant 适合生产部署（过滤能力强），sqlite-vec 适合轻量场景和本地演示（零部署成本），pgvector 适合已有 PostgreSQL 的团队。选型跟着部署形态走,没有绝对优劣。

## 溯源：让每个回答可追责

企业场景对"答案从哪来"的要求是硬性的。我的做法：

- 检索到的每个 chunk 带 metadata 进 prompt，回答时要求引用来源
- 前端把引用渲染成可点击的原文链接，用户能一键跳到原始工单/Wiki
- **检索证据写入审计日志**——出了错误回答，能回放当时检索到了什么、模型看到了什么

第三点在排查 badcase 时价值巨大：大部分"模型胡说"最后查出来是"检索喂错了料"。没有检索日志，你连问题在检索层还是生成层都分不清。

## 评测：没有评测集的 RAG 是在裸奔

改一版 prompt、换一个 embedding 模型、调一次检索阈值——变好了还是变坏了？没有评测集就只能靠感觉。

最小可行的评测体系：

1. **构建测试集**：从真实用户问题里挑出有标准答案的 case（我从客服历史工单里整理），覆盖高频意图和已知 badcase
2. **检索评测**：标准答案对应的文档有没有进 top-k（命中率、MRR）
3. **端到端评测**：生成的回答和标准答案的一致性（人工 + LLM judge 混合）
4. **回归机制**：每次改动跑一遍，新 badcase 进测试集

这套东西不复杂，但它把 RAG 迭代从"玄学调参"变成"有数字的工程"。

## 踩坑记录（真实事故现场）

**坑 1：第三方系统没有 API。** 想把 Redmine 某插件的数据入库，发现插件没实现 REST 端点，带 API Key 也是 403，HTML 页面还强制要求登录 cookie。教训：抓数据之前先 curl 测一下端点，别浪费时间找"怎么带 Key"。工程上留了三条路：跳过（数据量够就不硬抓）、导出浏览器 session cookie 爬、找管理员开 API。

**坑 2：macOS 自带 SQLite 不支持 loadable extension。** 用 sqlite-vec 时 `enable_load_extension` 直接报 `not authorized`——Apple 编译系统 SQLite 时禁了扩展加载。解法：`pip install pysqlite3-binary` 然后在入口处替换 `sys.modules["sqlite3"]`。

**坑 3：API Key 没配时报错路径很诡异。** 向量库加载正常、检索正常，最后在 embedding 调用处才抛 AuthenticationError。教训：外部依赖在启动时做健康检查，别让配置问题伪装成运行时 bug 深埋在链路中段。

## 总结成三句话

1. **Chunk 策略和 metadata 决定检索质量上限**，检索算法只是在这个上限内优化
2. **混合检索是生产标配**，GraphRAG 按需上，别为了技术新鲜度加复杂度
3. **溯源和评测不是锦上添花**，它们是"可信"两个字的全部来源

RAG 这个词已经被讲烂了，但生产级 RAG 的工程含量被普遍低估。上面每一条都对应我踩过的一个坑——希望能帮你少踩几个。
