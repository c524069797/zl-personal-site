## 为什么 AI 工程师也要懂这条链路

我的主业是 AI Agent 开发。做 Agent 时有个绕不开的现实：Function Call 对接的就是订单服务、库存服务、工单服务这些后端接口。不清楚接口背后的业务语义、数据模型和边界条件，Agent 设计出来就是不可靠的——它会在订单不允许退款的状态下去创建退款单，会把重复回调当成两笔支付。

所以这篇不讲模型，讲业务。沿着"一个订单的一生"这条主线，把电商后端的核心概念串一遍。

## 订单的一生

```
流量 → 转化 → 履约 → 售后 → 复购
```

| 环节 | 发生什么 | 涉及系统 |
|------|---------|---------|
| 流量 | 站内搜索/推荐、站外买量、直播种草 | 搜索、推荐、广告投放 |
| 转化 | 商详页 → 加购 → 下单 → 支付（层层掉人，叫"漏斗"） | 商品、购物车、交易、支付 |
| 履约 | 拆单、仓储拣货、发货、物流 | OMS 订单、WMS 仓储、TMS 物流 |
| 售后 | 退换货、退款、客诉 | 客服工单、逆向物流 |
| 复购 | 会员、优惠券召回、私域运营 | CRM、营销系统 |

## 下单之后，后端发生了什么

用户点"提交订单"之后的完整链路，这条线能串起电商后端的大部分概念：

```
1. 网关层：限流、鉴权（挡住超量请求，防止系统被冲垮）
2. 订单服务：创建订单，写 MySQL，状态 = 待支付
3. 库存服务：锁库存（Redis 预扣 + MySQL 落库，防超卖）
4. 营销服务：核销优惠券
5. 支付服务：对接微信/支付宝，用户付款
6. 支付回调：订单状态 → 待发货
7. 订单服务发一条消息到 RocketMQ
8. 下游各自消费：仓储拣货发货、积分服务加积分、通知服务发短信
9. 物流轨迹更新 → 确认收货 → 交易完成，进入售后期
```

第 7 步为什么用消息队列？下单的核心动作只有"创建订单 + 扣库存 + 支付"，加积分、发短信这些事没必要让用户等——扔进队列异步做。大促时请求洪峰先堆在队列里，下游按自己的节奏消费，这就是**削峰填谷**。

## 五个必懂的业务难题

### 1. 超卖：100 件库存不能卖出 101 件

大促瞬间 1 万人抢 100 件库存。解法：库存预先加载到 Redis，下单时用 Redis 原子操作（Lua 脚本）预扣减——扣到 0 直接拒绝后面的请求，扣成功的才去 MySQL 走真正下单。

要点一句话：**用 Redis 的单线程原子性挡住并发，MySQL 只处理"已抢到资格"的少量请求。** 秒杀系统整体就是"漏斗式泄洪"：网关限流拦掉 90% → Redis 预扣防超卖 → MQ 排队削峰 → 订单服务异步落库，每一层都在减少到达下一层的流量。

### 2. 缓存三兄弟：穿透、击穿、雪崩

- **穿透**：疯狂查询一个根本不存在的数据（如 id=-1），缓存永远没有，每次都打到数据库。解法：布隆过滤器拦截，或缓存空值。
- **击穿**：某个热点 key（爆款商品）恰好过期的瞬间，洪峰全部打到数据库。解法：互斥锁只放一个请求去查库回填，或热点 key 永不过期。
- **雪崩**：大量 key 同一时刻集体过期。解法：过期时间加随机数打散。

顺带一个必考题：Redis 和 MySQL 不一致怎么办？标准做法是 **Cache Aside：先更新 MySQL，再删除缓存**。反过来"先删缓存再更新库"在并发下会被读请求把旧值重新塞回缓存，造成长期脏数据。

### 3. 幂等：回调重复推送 3 次，不能发 3 份货

微信支付的回调通知可能重复推送。解法：用唯一单号做判断——处理前先查状态，已处理就直接返回成功，数据库唯一索引兜底。

**幂等是所有交易系统的地基。** 这个概念的迁移性极强：制造业里扫码报工防重复提交，用的是同一套解法。

### 4. 订单超时自动关闭

15 分钟未支付自动取消订单并释放库存。定时任务扫表是低级答案（量大扫不动、延迟高），主流方案是 **RocketMQ 延迟消息**：下单时发一条 15 分钟后投递的消息，消费时检查订单状态，未支付则关单。

### 5. 对账：钱的事不能只靠代码正确

每天和支付渠道核对账单，找出"我这边有单渠道没钱"（掉单）或"渠道有钱我没单"（长款）的差异并补偿。分布式事务在电商大多用最终一致性（消息队列 + 重试 + 对账补偿），允许短暂不一致，靠对账兜底最终对齐。强一致方案太重，大多数场景用不上。

## 子系统业务地图

| 子系统 | 业务本质 | 一句话要点 |
|--------|---------|-----------|
| 商品 | 卖什么 | SPU/SKU 模型、类目属性、上下架审核流 |
| 购物车 | 想买什么 | Redis Hash 存储；未登录存本地、登录后合并 |
| 交易/订单 | 买卖契约 | 状态机流转；多商家要拆单；退款单是"逆向订单" |
| 库存 | 有没有货 | 预扣（下单锁定）与实扣（支付扣减）两段式 |
| 营销 | 促成交 | 优惠券生命周期：发放→领取→锁定→核销/退回；难点是预算控制和防刷 |
| 支付 | 钱怎么进来 | 渠道对接、异步回调、幂等、日终对账 |
| 风控 | 防坏人 | 黄牛、羊毛党；设备指纹 + 规则引擎 + 模型 |
| 搜索/推荐 | 人找货/货找人 | ES 搜索；推荐是"召回 → 排序"两段式 |
| 客服工单 | 售后兜底 | AI Agent 的落点；工单流转、SLA 时效 |

## 我的全栈视角

流量从哪来、页面怎么承接转化、下单之后订单怎么流转、库存怎么防超卖、大促怎么削峰——这条链路打通之后，你看任何一个业务系统都有了坐标系。

对做 AI 的人来说，这个坐标系直接决定 Agent 的可靠性上限：意图识别识别的是业务动作，工具调用调的是业务接口，敏感操作管控依据的是业务规则。业务理解不是加分项，是 Agent 工程的一部分。
