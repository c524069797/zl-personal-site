## 提示词里的"请确认"保护不了任何人

见过不少 Agent 项目的"安全设计"是在系统提示词里写一句："执行敏感操作前请先向用户确认。"

这不是安全设计，这是许愿。模型可能遵守，也可能在某次长对话后忘掉，或者被一句"我已经确认过了"绕过。**真正的安全边界必须建在模型之外**——模型可以犯错，但架构要保证错误到不了生产数据。

我在两个项目里落地过这套思路：企业 Agent 支持平台（客服场景，敏感操作是数据导出、退款类动作）和智能备份 Agent（运维场景，敏感操作是恢复/覆盖数据）。这篇把方法论拆成三件套：HITL 审批、权限边界、审计日志。

## 第一件：HITL——状态机层面的硬中断

HITL（Human-in-the-Loop）的正确实现位置是**编排层，不是提示词层**。

用 LangGraph 的做法：敏感操作节点执行前调用 `interrupt()`，整个状态图在这里暂停，生成一份待审批载荷（谁发起、要做什么、影响范围），然后把状态通过 checkpointer 持久化。人工通过审批接口决策后，图从中断点恢复执行——同意则继续，拒绝则走终止分支。

几个工程细节：

- **checkpointer 按 thread 保存会话状态**，审批可能发生在几分钟甚至几小时后，恢复时条件入口直接跳过前置节点继续执行，不重跑整个链路
- **审批前动作真实不会执行**。这是硬中断和提示词确认的本质区别：不是"模型答应先问一下"，而是代码路径上根本走不到执行那一步
- **分级触发**：客服场景按金额分级（小额自动过、大额必审批）；备份场景按操作性质分级（查询直接执行、恢复/删除必确认）

备份场景把这个问题推到极致：恢复操作会覆盖现有数据，误操作是最致命事故。我的规则写成一句话就是——**不确认绝不落盘**。恢复动作用 `interrupt()` 中断等人工确认，同时工具层再加一道 `confirm` 参数的二次门控，就算模型或调用方绕过了编排层，工具层也会拒绝执行。安全设计要做冗余，单点防线不可信。

## 第二件：权限即能力——RBAC 派生 Agent 边界

企业里不同角色能干的事不一样，Agent 也必须如此。我的设计是**把 Agent 能力当成权限系统的派生物**：

- RBAC 角色定义里加一类 `agent:*` 的能力 scope
- 用户登录后，其角色决定了会话里 Agent 可见可用的工具集——销售角色的 Agent 调不出财务数据导出工具，这个工具对它根本不存在
- 岗位 Agent（按部门/职能预设的 Agent 形态）同样按登录者权限裁剪

这个设计的关键收益是**把"Agent 越权"从行为问题变成配置问题**。不需要靠提示词约束"你不能查财务数据"，而是那个工具压根没注册进这个会话的工具列表。攻击面直接消失。

反过来说，任何"全体用户共享一个全能 Agent，靠提示词区分权限"的设计，在企业场景都过不了安全评审——提示词注入随便一试就穿。

## 第三件：审计——每一步都留痕

企业级系统的底线要求：出了事能查。Agent 引入后审计范围要覆盖三层：

1. **对话层**：每次问答的完整记录，含用户、时间、会话 thread
2. **执行层**：每次工具调用的操作者、对象、参数、结果、风险级别、耗时
3. **检索层**：RAG 检索到的证据写入日志——回答出错时能回放"当时模型看到了什么"

第三层最容易被省略，但它是排查 badcase 的核心依据：大部分"模型胡说"最后查出来是检索喂错了料。没有检索日志，问题在检索层还是生成层都分不清。

审计日志同时是评测体系的数据源：badcase 从日志里来，进回归测试集，形成"线上问题 → 测试用例 → 版本验证"的闭环。

## 三件套的组合拳

单独看每一件都不新鲜，组合起来才是完整的安全模型：

```
用户请求
  → 权限边界裁剪工具集（越权操作从源头不存在）
  → Agent 推理 + 工具调用（每步写审计日志）
  → 敏感操作触发 HITL 硬中断（审批通过才执行）
  → 执行结果 + 检索证据全量留痕
```

一个真实的运行示例（备份 Agent）：用户说"把昨天的备份恢复到生产目录"。意图识别 → 规划节点生成恢复方案 → 策略决策节点判定这是破坏性操作 → `interrupt()` 中断，生成待确认载荷（恢复哪个快照、覆盖哪些路径、影响多少文件）→ 用户确认 → 从断点恢复执行 → 校验汇报节点核对恢复结果 → 全程审计入库。任何一步的"不"都会让数据保持原样。

## 容错率决定架构，不是模型能力

最后说一个更大的判断。不同场景对 Agent 的容错要求差几个数量级：电商客服答错一句，转人工就行；制造业工艺参数推荐错了，可能报废一批物料；备份恢复做错了，生产数据直接没了。

所以"Agent 能不能全自动"从来不是模型能力问题，是场景容错率问题。**模型越强，越需要清晰的边界设计**——因为它会被授予更多能力，单次错误的杀伤半径更大。

我的实践结论：高价值场景的 Agent 架构，从第一天就要把 HITL、权限、审计设计进去，而不是出了事故再补。这三件套加起来的开发量并不大（LangGraph 的 interrupt + checkpointer 已经把最难的状态恢复做掉了），但它决定了你的 Agent 是"演示品"还是"生产系统"。
