# OpenCodeReview 与安全审计：让 Agent 的结论有证据可复核

编码 Agent 很快就能写出一份评审意见：这里可能空指针，那里缺少权限校验，某段查询需要改进。真正落到研发流程里，开发者还需要判断问题是否存在、位置是否准确、影响是否被夸大，以及修复会不会改变业务行为。

[OpenCodeReview](https://github.com/alibaba/open-code-review) 和 [Cloudflare security-audit-skill](https://github.com/cloudflare/security-audit-skill) 分别提供了两个学习入口：前者组织代码变更评审，后者组织覆盖率与独立验证。把它们接在同一条订单链路上，更容易观察 Agent 的推断怎样转成可复核的工程结论。

> 本文归档于 2026 年 9 月，资料核对于 2026-10-14。内容基于官方文档分析；缺陷注入、评审与 CI 方案均为练习设计，尚未运行，不包含个人测试得到的准确率或 Token 数据。

## 先准备两个明确的问题

继续使用 [Ponytail 阶段](/blog/ponytail-agent-scope-control) 的小型后端，以及 [Archify 阶段](/blog/archify-verified-architecture-dataflow) 核对过的请求链路：一个订单查询 API、一张订单表、JWT 身份和订单归属校验。

只在本地练习分支中准备两种变更：

| 类型 | 练习中准备的缺陷 | 预期验证 |
| --- | --- | --- |
| 普通业务缺陷 | 查询没有结果时直接访问订单字段 | 原本应返回 404 的输入触发异常 |
| 安全问题 | 查询条件去掉当前用户 ID，仅按订单 ID 查找 | 用户 A 能读到虚构用户 B 的订单 |

选择越权问题，可以直接沿用已有业务契约。它同时要求检查可信身份、数据查询和输出三处，适合观察评审工具是否理解“用户只能查看自己的订单”。

两种缺陷分别放在不同变更里，保留已知答案与对应测试。修复后再次审查，检查工具是否继续报告已经消失的问题。所有身份和订单都使用本地虚构数据。

## OpenCodeReview 怎样组织一次评审

官方文档把它描述为确定性工程与 Agent 的混合架构。程序负责文件选择、相关文件分组、规则匹配和评论定位等约束；Agent 负责结合上下文判断问题，并按需读取代码。规则匹配为模型提供审查方向，不能据此推断每条业务规则都由静态程序直接判定。[官方设计说明](https://github.com/alibaba/open-code-review/blob/main/README.md#core-design-deterministic-engineering--agent-hybrid)

可以把职责理解成以下流程，具体调用顺序以使用版本为准：

```text
Git 变更
   ↓
确定评审文件与相关分组
   ↓
按文件特征匹配规则
   ↓
Agent 获取上下文并提出问题
   ↓
定位与反思处理
   ↓
结构化评论
   ↓
人工复核与回归测试
```

订单越权的判断需要额外业务信息：身份来自哪里，订单归属规则是什么，上游是否已经做过检查。只看到查询中没有 `owner_id`，还需要继续核对其他控制层，才能确定越权路径是否成立。

确定性程序适合约束文件范围、格式和位置。模型适合补充上下文理解。两者组合后，仍需用测试或源码证据判断最终结论，格式正确的评论也可能包含误判。

## 一次本地评审应留下什么

按官方说明配置模型后，可对工作区变更执行以下命令。这里仅列出练习入口，不代表本文已执行，也不直接安装或调用模型。

```bash
ocr review --format json --output review-result.json
```

这类工作区评审包含已暂存、未暂存和未跟踪的变更。固定分支范围时，则使用对应的 `--from` 与 `--to` 参数，避免把其他工作混入结果。[CLI 使用说明](https://github.com/alibaba/open-code-review/blob/main/README.md#quick-start)

拿到结果后，逐条填写复核表：

| 检查点 | 要保留的依据 |
| --- | --- |
| 问题真实存在 | 能说明错误行为的输入、输出或源码路径 |
| 文件和行号准确 | 本次评审提交中的具体位置 |
| 业务上下文准确 | 订单归属契约、身份来源与查询条件 |
| 缺陷类型清楚 | 空值处理错误、跨用户读取或其他明确结果 |
| 修复可验收 | 修复前失败、修复后通过的同一条测试 |
| 尚待人工判断 | 工具缺少的配置、上下游控制或运行事实 |

行号需要绑定源码版本。文件后来增加几行，旧行号可能失效；代码没有变化，评审也可能误把旧路径当成当前路径。保留提交、工具版本、模型配置名称和结果文件，可以减少这类复核成本。

## 精度、召回率与成本怎样比较

这里先用业务缺陷与越权两个已知问题校准输出，目标是看清行为，样本不足以评估通用能力。

精度关注“报告出来的问题中，有多少是真的”；召回率关注“已经存在的问题中，有多少被发现”。减少评论数量可能降低噪声，同时也可能漏掉问题，需要两项一起观察。

官方 README 的基准介绍明确提到偏向精度、接受较低召回率的取舍。其结果受数据集、模型和评审方式影响，本地项目应单独记录人工确认率、已知缺陷命中情况、耗时及可获得的 Token 消耗，不能照搬官方数字。[官方基准说明](https://github.com/alibaba/open-code-review#benchmark)

对团队而言，还应记录每条评论的人工处理时间。十条真实但重复的意见，和一条定位准确、能直接验证的问题，带来的研发成本差别很大。

## 阅读 ASSURANCE_CASE，理解评审工具自己的边界

评审工具也会接触不可信内容：仓库里的文本、模型返回的路径和评论，以及本地查看器收到的请求。[ASSURANCE_CASE.md](https://github.com/alibaba/open-code-review/blob/main/ASSURANCE_CASE.md) 从这些信任边界解释了路径约束、响应校验、凭据处理和查看器防护。

这份文档值得学习的是“主张对应哪条控制和证据”。它是项目维护者对自身设计的论证，评估具体版本时仍应核对相关实现与检查结果。

接入自己的 CI 时，也要明确哪些代码会发往配置的模型服务，哪些凭据由运行环境提供。练习不需要把真实业务数据或身份材料放进评审输入。

## security-audit-skill 的六个阶段

Cloudflare 的项目把完整审计组织成六个阶段。架构图和覆盖率台账先建立范围，候选发现与验证随后推进，最终报告从已复核的记录生成。[官方流程](https://github.com/cloudflare/security-audit-skill#what-it-does)

1. **架构侦察**：识别入口、信任边界与数据路径，写入 `architecture.md` 和初始覆盖率台账。
2. **按覆盖率台账发现候选**：分配检查单元，记录已检查路径并查找遗漏。
3. **独立验证候选**：让新的验证者核对根因、阻断条件和最小可观察结果。
4. **结构化输出**：将得到独立结论的记录写入 `findings.json`，执行契约校验。
5. **独立复核最终记录**：重新核对路径、条件、结果和结论，避免整理报告时改变事实。
6. **生成最终报告**：根据已验证的记录与覆盖率台账说明问题、范围和未完成项。

独立验证有一个明确目的：给候选寻找反证。原来的判断者容易顺着已有假设继续解释，新验证者需要检查是否存在上游权限控制、不可达路径或遗漏的前提。

## 四份文件，各自承担什么责任

学习时，先分清运行产物和校验契约：

| 文件 | 性质 | 阅读重点 |
| --- | --- | --- |
| `architecture.md` | 针对目标仓库生成的产物 | 入口、可信身份、资源与边界 |
| `coverage-ledger.json` | 针对本轮检查维护的台账 | 检查过什么、证据在哪里、哪些仍未覆盖 |
| `findings.json` | 经验证形成的结构化结论 | 路径、前提、观察结果和最终状态 |
| `report-schema.json` | Skill 仓库提供的契约 | 各状态允许和必须包含的字段 |

前三份文件在审计自己的目标时产生，不能把它们当成下载 Skill 后就已有的目标审计结果。生成和更新它们还需要保持台账与结论一致。[Skill 设置与文件职责](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/SKILL.md#full-audit-setup)

结论分为 `confirmed`、`needs_validation`、`rejected`。确认项需要完整证据；待验证项需要写清决定性的缺口，且不附严重等级；被反证的候选保留否定理由。具体字段以 [report-schema.json](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/report-schema.json) 为准。

官方流程还要求对记录与覆盖率台账执行确定性校验。校验通过支持格式与一致性结论，漏洞是否真实仍取决于源码路径和验证证据。[验证与报告说明](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/VALIDATION-AND-REPORTING.md)

## 一条订单越权结论需要哪些证据

对练习中的候选，可以按顺序核对：入口确实接受订单 ID；用户 A 的身份能够通过有效鉴权；查询没有限制订单归属；不存在其他阻断层；返回路径确实包含用户 B 的订单内容。

如果只能证明查询缺少条件，却无法确认返回之前是否还有校验，就继续追踪源码。依赖仓库之外的部署事实时，应准确记录尚未确认的条件。不能把推测写成已经发生的越权。

源码检查保持只读。动态复核只使用自有仓库、虚构数据与隔离的本地测试，按 Skill 的执行边界检查沙箱能力；无法满足条件时记录阻塞事实和验证方案。练习到最小错误结果即可，不需要访问线上账户或外部目标。[执行边界](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/SKILL.md#universal-execution-safety)

修复可以回到一个小而明确的不变量：订单查询必须受可信用户身份约束。将归属条件放到真实数据访问路径，补上跨用户读取的回归测试，再检查空结果响应是否仍符合契约。

## CI 接入先保留人工判断

初次接入时，让确定性的构建、测试和格式检查承担门禁，Agent 评论作为评审输入。先保留一段时间的误报、漏报和返工记录，再决定哪些经过校准的结论值得影响合并策略。

CI 至少需要固定评审范围、保留结构化结果、限制可用凭据，并区分“没有发现问题”“评审没有完成”和“模型调用失败”。对外部分支贡献，先只运行不需要敏感凭据的检查；需要模型凭据的审查由受信任流程安排，避免直接把秘密交给贡献者控制的执行内容。

安全审计则按明确范围单独组织，保留未覆盖与待验证项。没有候选问题的结果，也只能说明本次范围内没有形成已确认结论。

这一阶段的完成标准很具体：能够复核两条已知缺陷，解释规则与 Agent 各自负责什么，并指出每条结论的证据、遗漏条件和修复测试。做到这一步，再考虑增加扫描范围。
