# Ponytail：让编码 Agent 先控制实现范围

一个订单查询接口缺少归属校验，需求本身很小。交给编码 Agent 后，它却可能顺手增加权限框架、统一仓储接口、缓存层和几份配置文件。功能看起来更完整，理解和维护的成本也跟着增加。

我更关心一个具体问题：怎样让 Agent 在完成业务要求的同时，控制新增代码和实现范围？[Ponytail](https://github.com/DietrichGebert/ponytail) 提供了一组值得研究的约束，适合放在 Agent 工程学习的第一步。

> 本文归档于 2026 年 9 月，资料核对于 2026-10-14。下面的对照实验是练习设计，尚未执行；不包含个人实测的节省比例。

## 四个项目，用同一条业务链路学习

这组学习可以拆成四项工程能力：

| 项目 | 要练习的能力 | 最终应留下的东西 |
| --- | --- | --- |
| Ponytail | 控制实现范围，减少过度设计 | 两次实现的变更与验收对照 |
| Archify | 表达并核对架构、数据流 | 能对应源码的图与证据表 |
| OpenCodeReview | 把 Agent 接入代码评审与 CI | 逐条复核过的评审意见 |
| security-audit-skill | 组织可复核的安全审计 | 覆盖率台账与有证据的结论 |

先完成一项，再推进下一项。每个项目都换一套业务，会把大量时间花在重新理解代码和准备环境上。贯穿同一个小型后端，可以持续观察同一处鉴权、查询和错误处理怎样变化。

练习项目只保留一条接口：`GET /api/orders/{id}`。数据库只有一张 `orders` 表，字段为订单 ID、归属用户 ID、状态和金额；金额使用整数分。JWT 鉴权已有实现，当前用户来自验签后的身份信息。应用代码与测试合计控制在几百行，暂不增加管理后台、支付、消息队列和独立权限服务。

接口的业务要求也很明确：用户只能查看自己的订单。未登录或令牌无效返回 401；不存在的订单与其他用户的订单统一返回 404。这是这次练习选定的接口契约，用来避免暴露其他用户的订单是否存在。

## 先读决策阶梯，再看安装方式

Ponytail 的核心入口是 [skills/ponytail/SKILL.md](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)。读它时，可以把实现选择整理成六个检查点：

1. 这部分功能是否确实在需求内？没有被要求的扩展先不加入。
2. 项目里是否已有组件、服务或辅助函数？优先沿用现有模式。
3. 标准库或平台能力是否能满足要求？同时遵守项目已经建立的约定。
4. 已安装的依赖是否足够？新增依赖需要有具体收益。
5. 能否用读者一眼能理解的简单表达完成？避免为了短而压缩可读性。
6. 前面的选择都不成立，再写必要的新实现。

这套顺序适合用来检查 Agent 的设计过程。它要求先理解相关代码和调用关系，再选择改动方式；校验、错误处理、安全边界和必要测试仍属于完整交付的一部分。[官方 Skill](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)

映射到订单接口，最值得追问的地方是：身份解析是否已有公共入口？查询方法能否直接加入 `owner_id` 条件？异常响应是否已有统一格式？只有一个订单归属判断时，为什么需要一套可配置的权限策略？

这些问题能把讨论从“架构是否高级”拉回具体业务。新抽象必须解决当前可证明的问题，才能抵消额外的维护成本。

## 用同一任务做两次

准备两个从同一干净提交开始的独立工作目录，各自使用临时测试数据。第一轮关闭 Ponytail，第二轮启用 Ponytail；模型、版本、任务描述和验收条件保持一致，使用新的会话，避免第二轮直接继承第一轮的答案。

可以给两轮同样的任务：

```text
补齐 GET /api/orders/{id} 的订单归属校验。
当前用户必须来自已经验签并检查有效期的 JWT。
用户只能读取自己的订单；查不到和不属于当前用户均返回 404。
保留既有响应格式，补充直接验证这些行为的测试。
不要增加其他业务功能。先说明准备复用的现有能力，再修改代码。
```

两轮都遵守相同的安全与验收要求。第一轮代表现有工作方式，第二轮增加 Ponytail 的范围控制约束。比较结束后，记录 Skill 的来源版本和启用方式；不同 Agent 宿主加载 Skill 的方式可能有差别，需要确认它确实进入了本轮上下文。[安装说明](https://github.com/DietrichGebert/ponytail/blob/main/INSTALL.md)

这仍然只是一次小样本对照。模型输出存在随机性，先后顺序和上下文也会影响结果。若要得出稳定结论，需要重复运行并保留原始变更，不能凭一次输出就认定某个 Skill 总能节省成本。

## 验收先看行为，再看变更规模

先让两份实现通过同一组检查：

| 输入或条件 | 预期行为 | 对应业务边界 |
| --- | --- | --- |
| 有效身份查询自己的订单 | 200，字段与金额准确 | 正常查询可用 |
| 缺少令牌、签名无效或令牌过期 | 401 | 身份校验有效 |
| 查询其他用户的订单 | 404，不返回订单内容 | 归属隔离有效 |
| 查询不存在的订单 | 404 | 空结果处理正确 |
| 订单 ID 格式非法 | 400 | 参数校验有效 |
| 数据库访问失败 | 约定的服务端错误，不暴露内部连接信息 | 故障响应可控 |

数据库故障可以通过替换测试中的访问依赖来模拟，不需要破坏已有数据库。其他检查使用两个虚构用户和少量订单，确保身份与资源归属能被独立验证。

行为一致以后，再填写变更记录：

| 指标 | 未启用 Ponytail | 启用 Ponytail |
| --- | --- | --- |
| 修改文件数 | 待记录 | 待记录 |
| 应用代码增加与删除行数 | 待记录 | 待记录 |
| 测试增加与删除行数 | 待记录 | 待记录 |
| 新增依赖及用途 | 待记录 | 待记录 |
| 验收结果与遗漏条件 | 待记录 | 待记录 |
| 人工阅读和返工时间 | 待记录 | 待记录 |

应用代码、测试和生成文件应分别统计。测试行数增加可能意味着边界被补齐；锁文件变长也不能直接说明业务实现更复杂。

## 怎样识别无效代码

可以逐项检查新增内容：只有一个调用方的通用接口，是否简化了理解？新配置项是否存在第二种真实使用场景？缓存是否解决了已经观察到的延迟问题？新增权限框架是否承担了当前接口以外的明确职责？

如果两轮都能正确实现订单隔离，其中一轮直接复用身份解析和现有查询方法，另一轮增加多个没有业务用途的包装层，前者通常更容易评审。这个判断需要结合实际代码、测试结果和维护成本。

同时也要接受合理的增加：修补遗漏的异常路径、让多个调用方共享同一处安全校验、增加能捕捉越权的回归测试，都可能让改动变大。范围控制的目标是删除无效工作，保留业务正确性。

## 下一步只做一个可比较的改动

先选定这条订单接口，把两轮使用的任务、基线提交和验收条件固定下来。完成后只回答三个问题：两份实现是否满足同一业务契约？额外代码承担了什么职责？自己能否独立解释和修改最终实现？

有了这份变更，再进入 [Archify 的架构与数据流核对练习](/blog/archify-verified-architecture-dataflow)。代码范围足够小，图里的每个节点和连线才容易逐条核实。
